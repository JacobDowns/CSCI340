Why describe data as relations?

Relational vocabulary, keys, and data independence

An introduction to relational vocabulary, keys, and logical data descriptions that do not depend on a physical storage layout.
Author

CSCI 340

WEEK 2A · RELATIONAL VOCABULARY, KEYS, AND DATA INDEPENDENCE

Why use this abstract language at all?

The relational model gives us a precise way to say what information a system stores and how one piece of information identifies another. We can make those statements without committing to a particular file layout, data structure, or storage algorithm.

1. Begin with one relation

For now, use one familiar kind of information: students. Do not worry about compact notation yet.

student_id netid university_email display_name
2001 aria7 aria7@umontana.edu Aria Chen
2002 mateo3 mateo3@umontana.edu Mateo Ruiz
2003 priya11 priya11@umontana.edu Priya Shah

The terms below all describe different parts of this one display.

Attribute

An attribute is a named column of a relation: a named kind of information.

  • In this example, student_id, netid, university_email, and display_name are attributes.
  • An attribute name conveys a role. Even if both are stored as text, a netid and an university_email do not mean the same thing.
Domain

A domain is the set of allowed values for an attribute.

  • The domain of student_id contains student identifiers; the domain of university_email contains institution email addresses.
  • A domain conveys meaning, not merely a storage type such as text or integer.
  • For now, treat each attribute value as one indivisible value, rather than a list packed into a single cell.
Tuple

A tuple is a sequence of values, one for each attribute of a relation.

  • The first displayed tuple is (2001, aria7, aria7@umontana.edu, Aria Chen).
  • A tuple is the relational-model counterpart to what we casually call a row.
Relation

A relation is a named table - formally, a set of tuples over the same attributes.

  • The three displayed tuples form one possible relation named student.
  • A relation has no inherent row order, and it cannot contain two completely identical tuples.
Schema

A relation schema is a list of attributes and their corresponding domains that describes one relation’s logical structure.

  • The student relation schema says what kind of tuples may appear, not which ones exist today.
  • It is the description or blueprint, not the current data.
Instance

An instance is the particular set of tuples currently stored in a relation.

  • The three student tuples above are one instance of the student relation.
  • Tomorrow the instance may change while the schema remains the same.
  • At the next level up, a database schema is the logical structure of the whole database: its relation schemas and their rules. A database instance is the collection of relation instances at one moment in time.

Read the compact notation

Once the vocabulary is in place, we can write the student relation schema compactly:

\[ \text{student}(\text{student\_id},\ \text{netid},\ \text{university\_email},\ \text{display\_name}) \]

Read this as: “There is a relation named student with these four attributes.” The notation describes the relation schema. The table above shows one instance of that schema.

2. Keys identify tuples

Keys are statements about all valid instances of a relation, not merely the small sample on the screen. Suppose the university guarantees that student_id, netid, and university_email are each unique for a student.

Superkey

A superkey is one or more attributes whose values identify at most one tuple in every valid instance of a relation.

  • In student, {student_id} is a superkey because no two valid students share the same ID.
  • {student_id, display_name} is also a superkey. Adding display_name is unnecessary, but it does not stop the combination from identifying one student.
Candidate key

A candidate key is a minimal superkey: no proper subset of its attributes is a superkey.

  • {student_id}, {netid}, and {university_email} are candidate keys in this example.
  • {student_id, display_name} is not a candidate key because student_id alone already works.
  • Minimal means minimal within that set of attributes. It does not mean that no different superkey with fewer attributes exists: {A, B} and {C} could both be candidate keys if neither {A} nor {B} is a superkey.
Primary key

A primary key is the candidate key chosen as the principal means of identifying tuples in a relation.

  • If we choose student_id, it becomes the primary key.
  • The other candidate keys remain meaningful alternate identifiers.

Work through the examples

Attribute set Superkey? Candidate key? Why
{student_id} Yes Yes It uniquely identifies each student and has no extra attribute.
{netid} Yes Yes The institution guarantees one netid per student.
{display_name} No No Different students can share a name.
{student_id, display_name} Yes No student_id alone is already sufficient.
{university_email, display_name} Yes No university_email alone is already sufficient.

Class prompt: If two students can share a display_name, why does adding display_name to {student_id} not make the set less useful as a superkey? Why does it still fail to be a candidate key?

Practice 1: campus devices

Assume the university assigns every device a unique device_id. The manufacturer-assigned serial_number is also unique, but may be corrected or replaced during the device’s lifetime.

device_id serial_number device_type assigned_room
D100 SN-A1 Laptop Library 101
D101 SN-A2 Laptop Engineering 210
D102 SN-B8 Microscope Biology 114
D103 SN-C4 Projector Library 101

Class prompt: Identify superkeys and candidate keys for this relation. Which candidate key would you choose as the primary key?

Possible analysis
  • {device_id} and {serial_number} are candidate keys because each identifies one device without needing another attribute.
  • {device_id, device_type} is a superkey, but not a candidate key: device_id alone already identifies the tuple.
  • {device_type} is not a superkey because more than one device can be a laptop.
  • Either candidate key could be chosen, but device_id is a reasonable primary key because the university controls it and intends it to remain stable.
Practice 2: classrooms and a composite key

Assume a room number is unique only within a building. The pair building, room_number uniquely identifies a classroom.

building room_number capacity
Science 101 42
Liberal Arts 101 30
Science 202 42
Fine Arts 20 42

Class prompt: Identify superkeys and candidate keys for this relation. Which candidate key would you choose as the primary key?

Possible analysis
  • {building}, {room_number}, and {capacity} are not superkeys. Each can describe more than one classroom.
  • {building, room_number} is a superkey and a candidate key. Neither attribute can be removed while preserving uniqueness.
  • {building, room_number, capacity} is a superkey, but not a candidate key because the first two attributes already suffice.
  • {building, room_number} is the primary key here, and it is a composite key because it uses two attributes.

What a sample cannot prove

The three displayed names happen to be different, but that does not make display_name a key. A key depends on a rule about valid data, not a coincidence in the current instance. A later tuple could legitimately contain display_name = 'Aria Chen' again.

3. Link information across relations

One relation is enough to define tuples and ordinary keys. Systems become more useful when separate relations can refer to one another without copying all descriptive information into every tuple.

Consider these two relations:

For this example, student_id is the primary key of student, and section_id is the primary key of section.

\[ \text{section}(\text{section\_id},\ \text{course\_code},\ \text{term\_code},\ \text{section\_number}) \]

\[ \text{enrollment}(\text{student\_id},\ \text{section\_id},\ \text{enrolled\_on},\ \text{final\_letter\_grade}) \]

section_id course_code term_code section_number
501 CSCI340 2026FA 1
502 CSCI340 2026FA 2
610 MATH152 2026FA 1
student_id section_id enrolled_on final_letter_grade
2001 501 2026-08-17 A-
2002 501 2026-08-17 B+
2001 610 2026-08-18 A
Foreign key

A foreign key is an attribute, or group of attributes, whose values must match primary-key values in another relation.

  • In enrollment, student_id matches the primary key of student, and section_id matches the primary key of section.
  • The system should reject an enrollment that names a student or section that does not exist.
  • enrollment is the referencing relation; student and section are the referenced relations.
Referential integrity

A referential-integrity constraint requires values in specified attributes of one relation to appear in specified attributes of another relation.

  • A foreign-key constraint is a special case of referential integrity: the referenced attributes are the primary key of the referenced relation.
  • The foreign keys in enrollment enforce referential integrity with student and section.

This is a schema diagram: it shows relation schemas and the references among them, rather than individual tuples.

One tuple, several identifiers

In enrollment, neither student_id nor section_id identifies a tuple by itself: a student can enroll in several sections, and a section has several students. Together, {student_id, section_id} can be a candidate key if the rules allow at most one enrollment record per student per section.

Composite key

A composite key uses more than one attribute.

  • In this example, {student_id, section_id} is composite: both attributes are needed to identify one enrollment.
  • This relation has both a key of its own and foreign keys that point to other relations.

Class prompt: What would go wrong if an enrollment tuple used student_id = 9999 when no tuple with student_id = 9999 exists in student?

4. Why describe data this way?

Physical data independence

Physical data independence means that applications do not depend on the physical schema and need not be rewritten when the physical schema changes.

  • The schemas describe what a student, section, and enrollment tuple mean; which values identify tuples; and which values must refer to existing information.
  • They do not specify whether a DBMS uses files, pages, indexes, or another data structure internally.
  • If the physical arrangement changes while these facts and rules remain the same, applications should not need to be rewritten.

In his 1970 paper, E. F. Codd proposed describing shared data using mathematical relations while insulating users from many internal representation details. The formality is useful because it makes the logical design explicit enough to survive changes in implementation.

5. Put the ideas together

The main claim

The relational model is formal because it needs to state exactly what kinds of facts exist, what identifies them, and how separate pieces of information may be linked. That precision lets the logical design outlive a particular storage layout.

Looking ahead
